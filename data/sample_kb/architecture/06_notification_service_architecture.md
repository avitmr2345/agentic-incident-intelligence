# Notification Service Architecture

## Purpose

The Notification Service delivers user notifications generated by business events.

## Event-Driven Flow

```text
Order / Payment Service
        |
        v
  Message Broker
        |
        v
Notification Service
   |       |       |
 Email    SMS     Push
 Provider Provider Provider
```

The service consumes events such as order creation, payment completion, and payment failure.

## Processing

A notification consumer should:

1. receive the event
2. validate the event
3. determine the notification channel
4. deliver the notification
5. record processing state
6. retry transient failures
7. move persistent failures to a dead-letter path where configured

## Reliability

Important controls include:

- idempotent consumers
- bounded retries
- dead-letter handling
- provider timeouts
- correlation IDs
- queue monitoring

## Common Failure Scenarios

### Consumer stopped
Messages accumulate in the queue.

### Provider failure
The consumer is healthy but the external provider rejects or times out.

### Queue backlog
Notification latency increases even though API requests may remain healthy.

### Duplicate event
A retried message is delivered more than once. Idempotent processing prevents duplicate notifications.

## Investigation Signals

Check:

- queue depth
- consumer health
- processing latency
- retry count
- dead-letter messages
- provider response codes
- notification service logs
